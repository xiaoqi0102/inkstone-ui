# 06 · 设计方案（决策与理由）

> 这份文档回答的是「**为什么长这样**」——把选型、取舍、踩过的坑连证据一起记下来。
> 与 `03-设计语言.md`（速查）、`07-设计规范.md`（完整规范）的分工：
> **03 讲是什么，07 讲怎么用，06 讲为什么。**

---

## 1. 设计定位与气质

### 1.1 想给人什么感觉

| 关键词 | 怎么做 |
|---|---|
| **纸感、安静** | 浅色是暖象牙纸面 + 深棕墨字（不是纯白 + 纯黑）；一屏多留白，柔光只在边角 |
| **冷暖一支** | 全站中性色取暖，只留**一处钢蓝**当品牌色 —— 界面因此有焦点，又不花 |
| **克制** | 阴影比 Tailwind 默认收敛一档；动效只在状态变化时出现；一屏只允许一个渐变按钮 |
| **默认深色可读** | 深色主题同样是「暖炭」而不是蓝黑/绿黑；文字对比全程 ≥ AA |

### 1.2 明确不做

- 不做发光渐变、玻璃拟态堆叠（那是"AI 感"最重的两个套路）；
- 不做彩虹图表配色；
- 不引入外部字体（系统栈 + `tabular-nums` 足够，少一个网络依赖）；
- 不做多层嵌套导航；
- 不把业务逻辑塞进组件库。

## 2. 视觉方向与理由

### 2.1 为什么用 oklch

| 项 | 内容 |
|---|---|
| 选择 | 全站颜色写成 `oklch(L C H)`，`tokens.css` 里 40+ 个变量无一例外 |
| 理由 | oklch 的 L 是**感知亮度**，且与 C/H 解耦：做深色主题时只要压/提 L，颜色就"视觉等重"，不必重调色相 |
| 证据 | 品牌主色明暗两版：浅 `oklch(0.5000 0.0850 248.0000)` → 深 `oklch(0.7300 0.0850 248.0000)`。**C 与 H 完全没动，只把 L 从 0.50 提到 0.73** —— 这就是"只调亮度通道"的实操 |
| 代价 | oklch 需要现代浏览器（本项目 base 目标是现代浏览器）；导出给设计工具要转 hex，多一步 |

### 2.2 为什么是「暖纸 + 一处钢蓝」

配色骨架取自一组四色配色卡：灰蓝 `#C7D3DB` / 灰褐 `#A79A8A` / 象牙 `#FCF7DF` / 深棕墨 `#3E3630`。
四色刚好对上四个语义角色，于是映射关系是**一对一**的，不需要额外发明颜色：

| 卡上取色 | 落成的令牌 | 说明 |
|---|---|---|
| 象牙 `#FCF7DF` | `--background` / `--card` | 页面底 / 卡片底（卡片更干净一档，读作"纸上纸"） |
| 深棕墨 `#3E3630` | `--foreground` / `--sidebar` | 正文 / 导航轨道 |
| 灰褐 `#A79A8A` | `--muted-foreground` 一族的色相基准（H≈80） | 次要文字 |
| 灰蓝 `#C7D3DB` | **色相**留给品牌蓝（H 248） | 但**明度不能直接用**，见下 |

**关键一步：卡上的灰蓝不能用。** 它是很淡的灰调蓝（L≈86%），把它当主按钮底色、上面压近白字，对比度只有 2.60:1 —— 连 AA 都不到。
所以品牌蓝**沿用同一个冷色相方向、另行压深**到 `oklch(0.5000 0.0850 248.0000)`，取"清晰的钢蓝"；卡上那支淡蓝退居为"安静衬色"（出现在柔光、图表浅档里）。

| 深 / 浅 | `--background` | `--foreground` | 说明 |
|---|---|---|---|
| 浅色 | `oklch(0.9700 0.0150 92.0000)` | `oklch(0.3393 0.0153 59.1000)` | 暖象牙纸（H 92）+ 深棕墨字（H 59） |
| 深色 | `oklch(0.2250 0.0060 65.0000)` | `oklch(0.9350 0.0100 92.0000)` | 暖炭底（H 65）+ 米白字（H 92） |

**深色不是浅色的简单反色**：它同样是"暖"的（H 65 而非 240 的蓝黑），只是把 L 压到 0.225 —— 长时间盯屏时暖炭比纯黑/蓝黑更不刺眼。

### 2.3 色温铁律（本套配色成立的关键，也是踩过的坑）

> 全部**中性色**（底 / 卡 / 静默 / 描边 / 次级 / 抬升）色相统一落在 **暖带 55°~95°**；
> 品牌蓝与图表冷色统一落在 **冷带 248°~258°**。**只让品牌蓝当唯一的冷点。**

这条规则不是审美偏好，是被一次失败迭代逼出来的：**第一版**把页面底设成偏冷的灰蓝、卡片却是暖奶油色，
结果卡片内的进度轨、分隔线、输入框描边（当时用的是冷调中性色）与暖卡底"冷暖咬合"，整片**发脏**——
每个组件单看都没问题，摆在一起就是不对劲。

改成"中性色全员取暖、只留品牌蓝一个冷点"之后，冷暖关系从"互相打架"变成"有对比但同源"。
**改色时守住这两条色带**，比单独调某一个值更重要。

### 2.4 为什么图表五色 = 三档钢蓝 + 两支暖褐

| 令牌 | 浅色 | 深色 |
|---|---|---|
| `--chart-1` | `oklch(0.6800 0.0900 248.0000)` | `oklch(0.7600 0.0800 248.0000)` |
| `--chart-2` | `oklch(0.5700 0.1000 252.0000)` | `oklch(0.6600 0.0900 252.0000)` |
| `--chart-3` | `oklch(0.4600 0.0900 256.0000)` | `oklch(0.5500 0.0850 256.0000)` |
| `--chart-4` | `oklch(0.6800 0.0620 62.0000)` | `oklch(0.7400 0.0600 62.0000)` |
| `--chart-5` | `oklch(0.5200 0.0420 75.0000)` | `oklch(0.5800 0.0420 75.0000)` |

- **主序列（chart-1..3）**：同一冷带（248°→256°）**递降亮度**，读作"一套里的三个档"，多系列叠一起不打架，图例顺序自带"从亮到暗"的阅读顺序；
- **对比序列（chart-4..5）**：换到暖带（62° / 75°）——这条比"全部同色相"更有用：当两条线需要被**明确区分**时，冷暖对比比亮度差更可靠；
- **不要换彩虹配色**：在一个只有一支品牌色的界面里，彩虹图会显得像"别人的图"。

### 2.5 为什么背景要有柔光

`base.css` 里 `body::before` / `body::after` 两层大半径模糊光斑（品牌蓝 + 浅一档），给纯色底加"环境光"。
成本极低（两个 div 的 CSS），但一眼就有氛围，也让"暖纸"不至于平。

两条硬要求：① `pointer-events: none` 必须给，否则会吃掉点击；② 必须压到内容之下（`isolation` + `z-index: -1`），漏一个就会出现浮层遮挡 bug。

### 2.6 为什么全站隐藏滚动条 + 补偿要求

隐藏滚动条（`scrollbar-width: none` + `::-webkit-scrollbar { display:none }`）换来干净的边缘，
代价是**用户失去了"还有更多"的系统级提示**。所以内容区必须自己补：底部渐隐、总条数 `Badge`、
虚拟列表 `footer` 写"共 N 条"。**这是隐藏滚动条的配套义务，不是可选装饰。**

## 3. 关键设计决策记录（ADR）

### ADR ① 悬浮 Dock 导航，而非传统侧栏

| 项 | 内容 |
|---|---|
| 选择 | 手机底部居中横排胶囊、`md` 起变左侧竖排吸顶；同一份 DOM 靠断点切换 |
| 理由 | 后台工具的高频操作集中在少数几个页面，Dock 把导航压成一条、把横向空间全留给内容；移动端底部横排也更符合拇指可达区 |
| 代价 | 两个滑块（激活 + 悬浮）要手算位置；尺寸写死在 `--nav-offset-x/y`（移动端步长 2.75rem、桌面端 3.75rem）——**改尺寸必须同时改这两个数** |
| 坑 | 首次进入导航时，悬浮滑块必须先"在不可见状态下瞬移就位"再淡入（`flushSync` + `getBoundingClientRect()`），否则会看到一条横线从起点扫过去 |

### ADR ② 形变弹窗（卡片就地放大），而非居中 Modal

| 项 | 内容 |
|---|---|
| 选择 | `MorphingDialog`：触发器与弹窗共用同一个 `layoutId`，motion 插值位置与尺寸 |
| 理由 | "点哪儿长哪儿"保持了列表 → 详情的**空间连续性**，用户不会迷路（居中 Modal 会把上下文切断） |
| 代价 | 必须给 `MorphingDialogTitle`（无障碍），且只允许一层弹层 |

### ADR ③ 请求还原用「多行原始展示 + 可复制 curl」，而非 JSON 折叠卡片

| 项 | 内容 |
|---|---|
| 选择 | `RequestDetail` + `CodeBlock`：字段区（`<dl>`）+ 请求体（多行 `pre-wrap`）+ 可执行 curl，各自独立复制按钮 |
| 理由 | 排障时人要的是"**能直接粘到终端跑**"的东西，而不是再点开一层折叠 JSON |
| 代价 | 超长值会 `break-all` 断行——所以超长内容走 `CodeBlock` 而不是塞进字段区 |

### ADR ④ 页面动作用「上浮注册」，而非 prop 层层传递

| 项 | 内容 |
|---|---|
| 选择 | `usePageActions`（zustand）：页面里的动作注册到顶栏，而不是让布局层把 `actions` 一路传下去 |
| 理由 | 动作归**页面**所有；布局层不必知道业务按钮长什么样 |

### ADR ⑤ 隐藏滚动条

见 §2.6（含配套义务）。

### ADR ⑥ 明暗两套色各自调校，而非简单反色

| 项 | 内容 |
|---|---|
| 理由 | 对比品牌主色两版：浅 `L 0.50` / 深 `L 0.73`——**暗底上主色必须更亮**才压得住；`--card` 也是各调（浅 `0.9930` 近纸白 vs 深 `0.2750`，比深色底 `0.2250` 高一档，"纸上纸"的关系在深色下依然成立） |
| 附带规则 | **深色下的"危险色"要按与 `--primary` 同构的规则映射**：暗底上若沿用深红当文字色，实测只有 2.37:1，看不清。所以深色取**浅珊瑚红做面色/文字色 + 深棕做字**（`--destructive: oklch(0.8400 0.1200 30.0000)`），与浅色（`0.5500`）**不同值** |

### ADR ⑦ 标准件走「统一 radix 包 + 自写样式」，而非装单包或原样照搬

| 项 | 内容 |
|---|---|
| 背景 | `Tabs` / `Select` / `Popover` / `Accordion` / `Checkbox` 这类标准件任何后台都要用；常见坑是**同时**装了 `radix-ui` 聚合包和若干 `@radix-ui/react-*` 单包 |
| 选择 | 只依赖聚合包 `radix-ui`，样式全部重写到本库令牌上 |
| 理由 | 混装两套 radix 时，基元来自两个版本，类名/样式各走一套，主题化直接失控——**一次只保留一个来源** |

### ADR ⑧ 以「源码包」发布 + 库内一律相对路径，而非预编译产物

| 项 | 内容 |
|---|---|
| 选择 | `exports` 直接指向 `src/index.ts`；`npm pack` 出 `.tgz` 装进消费者项目；库内**不得出现 `@/` 别名** |
| 理由 | 消费者改一处令牌即可全局生效、无需等库发版；调试时直接跳到源码 |
| 代价 | 消费者要两行接线（`optimizeDeps.exclude` + `@source`），漏了 `@source` 会"能构建、不报错、但页面全裸样式"；且暂未产出 `d.ts` 之外的 lib 产物 |

### ADR ⑨ 用 `UIKitProvider` 收口 Provider 层次

| 项 | 内容 |
|---|---|
| 选择 | 根节点只包一层 `UIKitProvider`（内部 `主题 + Tooltip + 吐司`） |
| 理由 | 漏包 TooltipProvider 会让用到 `Tooltip` 的组件**直接白屏**（报 `Tooltip must be used within TooltipProvider`）。把这个坑收口在库里，而不是写在文档里让使用者自己踩 |

## 4. 复用与扩展的设计前提

### 4.1 必须继承的（设计语言本体）

| 项 | 内容 | 规模 |
|---|---|---|
| 令牌体系 | 语义化命名 + oklch + `@theme inline` 映射 | 40+ 变量：`--background/--foreground/--primary/--card/--border/--ring/--chart-1..5/--sidebar-*` |
| 色温铁律 | 中性暖带 + 品牌冷带（见 §2.3） | 两条色带 |
| 对比度口径 | 正文 ≥ 7:1、次要 ≥ 4.5:1、描边/轨迹 ≥ 1.15:1 | 见 07 §1.1.2 |
| 排版与图标阶梯 | 数字 `tabular-nums`、图标禁默认 24px | 见 07 §1.2 / §1.7 |
| 交互规则 | Dock 两滑块、标题只截断自己、请求还原三规矩 | 见 07 §2 |

### 4.2 可以替换的形态

导航形态、弹窗形态（形变 ↔ 居中）、详情面板布局、图标库（换掉 lucide 要同步尺寸阶梯）。

### 4.3 换品牌色：只改 3 个变量

`--primary` / `--accent` / `--ring`（浅深各一套 = 6 处），其余自动跟随。

| 步 | 动作 | 注意 |
|---|---|---|
| 1 | 换 `--primary` / `--accent` / `--ring` | `--ring` 与 `--primary` **保持同值**，一起改 |
| 2 | 守住色温铁律 | 新主色换到任何色相都行，但**中性色不要跟着改冷**（否则重演 §2.3 的"发脏"） |
| 3 | 复核 `--primary-foreground` / `--accent-foreground` | 它们是"主色上的字"，主色一变可能不够对比 |
| 4 | 复核 `--sidebar-primary`（浅色下与 `--primary` 不同值）与 `Badge` 的 success/warning（Tailwind 字面色，不是令牌） | 见 07 §5.2 |
| 5 | 重跑对比度校验 | 30 对语义色 + 主按钮渐变两端，**别靠肉眼** |

## 5. 已知取舍与将来可改进项

| # | 取舍 / 限制 | 影响 | 将来怎么做 |
|---|---|---|---|
| 1 | 以**源码**形式发布（ADR ⑧） | 消费者需两行接线，且依赖预编译失效会让冷启动稍慢 | 补 lib 模式构建（ESM + `d.ts` + 独立 CSS），仅在"对外分发"时才需要 |
| 2 | 图表色只有 5 档 | 超过 5 个系列要靠线型/透明度区分 | 加 `--chart-6+` 或引入序列生成工具 |
| 3 | 明暗两套色各自维护 | 换品牌色要改两处并两边各验一次 | 写一个 oklch 生成脚本：输入主色 H，自动产出两套 + 图表梯度 + 对比度报告 |
| 4 | **recharts 类名跨版本变化**（踩过的真坑） | recharts 2 用下划线式类名（`.recharts-cartesian-axis-tick_text`）、3 用连字符式（`.recharts-cartesian-axis-tick-value`）。用错版本**不报错、静默失效**：刻度字一直是默认 `#666`，深色下几乎看不清 | 已经改成"按 recharts 3 真实类名 + `var(--令牌)`"写在 `base.css`；**改这些选择器后必须用 `getComputedStyle` 实测渲染色**，别肉眼看 |

## 6. 一句话决策摘要

**令牌（oklch、暖中性 + 一处钢蓝、色温铁律）是硬约束；形态（导航、弹窗、详情面板）是可替换的外壳。
改色守两条色带、改完重跑对比度，就不会翻车。**
